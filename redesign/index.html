the object

It is a real little box, and it only does one thing.

It sits where the printer sits. Between customers it shows your own screen — logo, colours, the time. The moment your till has something to hand over, it shows the code instead, and then it goes back.

Your page goes to their phone. It never comes to us.

You already host the thing you hand over — a receipt, a ticket, a warranty, a menu. Your till sends us its address, not the page. We put a code on the counter. Their camera opens your page directly, from you.

  1. Your till sends the address. One request, carrying the link — not the page.
  2. We hold one credit and forward a command to that one box.
  3. The code appears on the counter and the box confirms it. That confirmation is what spends the credit — and how long it stays up is yours to set.
  4. They point a camera at it. No app, no account.
  5. Your page opens on their phone — fetched from you, directly. We never saw it.
sequence

The whole thing is one round trip and a sixty-second window.

What matters isn't the order of the steps, it's the timing — when the credit is held, when it is spent, and what happens if the box never answers. So here it is on a clock.

t = 0.0 s / idle scroll to run the clock

Held, not charged

The moment we accept the request one credit goes on hold. Your balance shows it, but nothing has been spent yet.

Spent on the showing

The box confirms the code is on screen, and that confirmation is what spends the credit. Not the request, and not the scan.

Released on silence

Nothing back inside the window and the command expires — the hold comes back in full and a late code never appears on the counter.

interface

One request. There is no second page of this.

No SDK, nothing runs on the device side. You hold a key, you name a box, you pass a URL.

# show a code on till 2
curl -X POST https://<host>/api/v1/devices/dev_8f21/trigger \
  -H "Authorization: Bearer sk_live_…" \
  -H "Idempotency-Key: 9f3a-…" \
  -d '{ "action": "show_qr", "payload": { "url": "…" } }'
202 accepted → { id, status: "queued" } → shown → settled

Retry it. Nothing doubles.

The idempotency key is required, not optional. Send the same one twice and you get the stored answer back — never a second charge, never a second code on the counter.

There is no status endpoint yet. That is deliberate at this stage, not an oversight. Billing reconciles itself because you are only ever charged for confirmed showings, and the console's ledger shows every command's outcome. If your integration needs a per-command status call, say so — it is on the roadmap.
